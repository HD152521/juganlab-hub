# 주간실험실 신뢰·안전 문서

작성: 2026-11-26. 대상: Supabase(Free) + 소셜 로그인 + 폼 업로드로 바꾸는 작업(아직 구현 전). 현재 PR 방식 검사(`lib/checks.mjs`, `scripts/check-submission.mjs`)의 점검 결과도 포함한다.
방향·결정은 [DIRECTION.md](./DIRECTION.md), 데이터베이스 초안은 [supabase/schema.sql](../supabase/schema.sql), 시험 목록은 [supabase/RLS-TESTS.md](../supabase/RLS-TESTS.md).

**범례**: 구현됨 = 이 저장소 코드에 이미 있음. 초안 = schema.sql 에만 있고 적용·실행 전. 계획 = 아직 코드 없음. **전문가 확인 필요** = 법률·약관 판단이 필요해 이 문서가 결론을 내리지 않는다.

## 1. 신뢰·안전 원칙

1. **"안전함", "검증됨"이라고 쓰지 않는다.** 화면에는 무엇을 언제 검사했는지만 적는다("자동 검사 통과 2026.11.26"). 자동 검사는 알려진 위험 신호만 잡는다. 건너뛴 검사(키 없음·시간 초과)도 "건너뜀"으로 그대로 적는다.
2. **설치파일·압축파일을 직접 호스팅하지 않는다.** 받는 것은 작품 정보(텍스트), 링크, 이미지(WebP)뿐이다. 설치는 공식 스토어나 GitHub Releases 페이지로 연결한다.
3. **로그인은 Google·GitHub 소셜만.** 비밀번호를 저장하지 않는다.
4. **신규 계정의 첫 작품은 운영자 승인 후 공개.** 승인을 받은 계정(`profiles.trusted`)의 이후 웹·앱 작품은 자동 검사 통과 시 바로 공개한다. 확장 프로그램은 항상 승인을 거친다(초안 결정, 11절).
5. **주소·링크를 바꾸면 재검사가 끝날 때까지 비공개.** 검사한 것과 공개하는 것이 같은지 `url_fingerprint` 로 확인한다(초안).
6. **신고가 들어오면 먼저 비공개, 그다음 검토.** 증거(신고 시점의 이름·주소)를 보존한다.
7. **비밀 키는 서버 쪽에만.** 프런트에는 공개(anon) 키만 둔다. `service_role` 키는 CI·Edge Function 의 비밀 변수에만 둔다. 저장소·문서·로그에 쓰지 않는다. 키가 노출되면 즉시 회전한다.
8. **개인정보를 최소로.** 공개 프로필에는 임의 이름(`maker-xxxxxx`)과 소개만 둔다. 이메일은 `auth.users` 에만 있고 API 로 노출하지 않는다.
9. **검사 코드도 공격 대상이다.** 사용자가 준 주소를 서버가 열어 보는 순간 서버가 공격 경유지가 될 수 있다(4절).

## 3. 저장·접근 규칙 요약 (schema.sql)

- 상태: `draft → checking → pending_review → published / rejected`, 신고·운영자 조치는 `hidden`.
- 사용자가 바꿀 수 있는 열만 열어 준다(작품 이름·소개·주소·링크·태그 등). `status`, `owner_id`, `check_summary`, `published_at`, `trusted`, `suspended_at` 는 열 권한이 없다.
- 상태 전환은 함수로만: 사용자 `submit_project`, 검사 서비스 `finish_check`(service_role), 운영자 `admin_review`·`admin_hide`·`admin_restore`·`admin_resolve_report`.
- 익명은 `published` 작품과 그 이미지·작성자 공개 열만 읽는다. 반려 사유·비공개 사유·검사 상세는 `project_reviews` 에 따로 두고 본인·운영자만 읽는다.
- 검사중·비공개 상태의 작품은 본인도 수정하지 못한다(검사 중 바꿔치기 방지, 신고 증거 보존).
- 알려진 한계: 이름·소개·설명 글의 수정은 재검사를 일으키지 않는다. 이미지 교체도 마찬가지다. 신고와 운영자 점검으로 대응한다.

## 4. 기존 검사 코드 점검 결과 (2026-11-26)

점검 파일: `lib/checks.mjs`, `scripts/check-submission.mjs`, `.github/workflows/check-pr.yml`, `check-main.yml`. 점검 전 기준 파일:줄은 보고서 참고. 아래는 항목별 결론이다.

| 항목 | 점검 전 | 조치 |
|---|---|---|
| 사설·루프백·링크로컬 주소 | IP 직접 입력은 거부했으나 `localhost.`(끝에 점), `a.localhost`, 점 없는 이름(`metadata`), `.lan` 등은 통과 | 이름 검사 강화(`isPrivateHost`) + 시험 |
| 이름이 내부 주소로 풀리는 경우(DNS 재바인딩 포함) | 검사 없음. 공격자 도메인이 `127.0.0.1`·`169.254.169.254` 로 풀려도 접속 | 연결 직전 이름 풀이 결과를 검사하고 그 주소로 그대로 연결(`lib/safe-fetch.mjs` `guardedLookup`) + 시험 |
| 리다이렉트로 내부 주소 이동 | `redirect: 'follow'`(기본 20회), 이동한 곳의 https 여부만 확인 | 리다이렉트를 직접 따라가며 매 단계 형식·내부 주소 검사, 최대 5회 |
| 시간 제한 | 헤더 수신까지만 12초. 본문 읽기에는 없음(GitHub 원본 파일을 `.text()` 로 읽는 구간) | 전체 12초, 본문 읽기까지 포함 |
| 응답 크기 제한 | 접속 확인은 본문을 버리지만, GitHub API·raw 파일은 크기 제한 없이 읽음 | 한도 초과 시 중단(`readCapped`) |
| 로그에 비밀 값 노출 | API 키(Safe Browsing)가 주소 쿼리에 들어가 오류·로그에 남을 수 있음. 작품 링크 이름(사용자 입력)의 줄바꿈으로 Actions 명령(`::...::`) 끼워 넣기 가능 | 키를 헤더로 이동, 오류 문장에서 비밀 값 가림, 로그 출력 시 줄바꿈·`::` 제거 + 시험 |
| 포크 PR 의 비밀 값 | `pull_request` 이벤트라 포크에는 비밀이 전달되지 않음. `GITHUB_TOKEN` 만 있고 `contents: read`. `pull_request_target` 미사용 | 문제 없음. 유지할 것 |
| 링크만 바뀐 경우 | `data/checks.json` 은 작품 주소(`url`)만 비교해 링크가 바뀌어도 7일간 재검사 안 함 | 주소+링크 묶음(`key`)으로 비교. 기존 기록은 다음 실행에서 한 번 재검사됨 |

**고치지 않고 남긴 것**

- PR 검사는 PR 이 가져온 `lib/`·`scripts/` 코드를 그대로 실행한다. 악의적 PR 은 검사기를 고쳐 통과시킬 수 있다. 운영자가 검사 관련 파일(`lib/`, `scripts/`, `.github/`) 변경을 직접 리뷰해야 한다(CODEOWNERS·브랜치 보호로 강제하는 것을 권장).
- `check-main.yml` 은 비밀(GSB·VT)을 쓰는 단계에서 사용자가 올린 주소를 연다. 내부 주소 접근은 막았지만, 비밀이 필요 없는 단계와 분리하면 더 안전하다.
- VirusTotal 에 주소를 제출하면 VT 에서 공개된다. 비공개 주소를 올리는 작품은 받지 않는 전제다.
- 외부 액션이 태그(`@v4`)로 고정돼 있다. 커밋 해시 고정을 권장한다.
- 서비스의 `ping` 주소는 방문자 브라우저가 호출하며 형식 검사(`https://`)만 한다. 폼 도입 시 사용자 입력 항목에서 제외한다.
- 비표준 포트는 막지 않는다.

## 5. 링크 허용·거부 규칙

구현 위치: 지금은 `lib/checks.mjs` `checkUrl`(형식), 허용 목록은 **계획**(폼 도입 시 같은 파일에 추가).

### 5.1 모든 링크에 공통으로 거부 (구현됨)

- `https:` 가 아닌 것(`http:`, `javascript:`, `data:`, `blob:`, `file:`, `ftp:` 포함)
- 주소에 계정 정보가 있는 것(`https://user:pass@host`)
- IP 주소 직접 입력(IPv4·IPv6, 10진수·16진수 표기 포함 — URL 파서가 정규화함)
- 내부 이름: `localhost`, `*.localhost`, `*.local`, `*.internal`, `*.lan`, `*.home.arpa`, 점 없는 이름. 끝의 점은 무시
- 이름이 내부 주소로 풀리는 것(사설·루프백·링크로컬·메타데이터 169.254.x.x·IPv6 내부 대역)
- 단축 주소: `bit.ly`, `t.co`, `tinyurl.com`, `goo.gl`, `ow.ly`, `is.gd`, `buff.ly`, `cutt.ly`, `rebrand.ly`, `shorturl.at`, `rb.gy`, `han.gl`, `url.kr`
- 열었을 때 파일이 내려받아지는 것: 확장자 `exe msi bat cmd scr ps1 apk dmg pkg jar vbs com zip rar 7z`, 응답이 `attachment` 이거나 `application/octet-stream` 등
- 접속 실패(HTTP 400 이상), 리다이렉트 5회 초과, 12초 초과
- Google Safe Browsing 위험 표시, VirusTotal 2개 이상 엔진 악성 판정

### 5.2 작품 종류별 허용 (계획)

| 종류 | 작품 주소 | 설치·다운로드 링크 |
|---|---|---|
| web | 공개 https 도메인(위 거부 규칙을 통과) | 해당 없음 |
| app | 스토어 허용 목록의 주소 또는 웹앱 주소 | 스토어 허용 목록만 |
| extension | 스토어 허용 목록의 주소 + **소스가 있는 GitHub 저장소 링크 필수** | 스토어 허용 목록만 |

### 5.3 스토어·배포 도메인 허용 목록 (초안 — 운영자 확정 필요)

| 구분 | 허용 호스트와 경로 |
|---|---|
| Chrome 웹 스토어 | `chromewebstore.google.com/detail/…`, `chrome.google.com/webstore/detail/…`(구 주소) |
| Firefox 부가 기능 | `addons.mozilla.org/…/addon/…` |
| Edge 부가 기능 | `microsoftedge.microsoft.com/addons/detail/…` |
| Google Play | `play.google.com/store/apps/details?id=…` |
| Apple App Store | `apps.apple.com/…/app/…` |
| Microsoft Store | `apps.microsoft.com/…`, `www.microsoft.com/store/apps/…`(구 주소) |
| 삼성 갤럭시 스토어 | `galaxystore.samsung.com/detail/…` |
| 원스토어 | `onestore.co.kr/…` (**도메인·경로는 게시 전 직접 확인**) |
| F-Droid | `f-droid.org/…/packages/…` |
| GitHub Releases | `github.com/<소유자>/<저장소>/releases` 와 `/releases/tag/<태그>` 페이지만. **`/releases/download/…`(파일 직접 받기)·`raw.githubusercontent.com`·`objects.githubusercontent.com` 는 거부** |

규칙: 호스트는 목록과 **정확히 일치**(부분 일치·접미사 일치 금지, `play.google.com.evil.example` 방지). 리다이렉트를 따라간 최종 호스트도 같은 목록 안이어야 한다. 위 목록 밖의 설치 링크는 받지 않는다. 목록은 이 문서가 기준이고, 바꿀 때 운영자가 승인한다.

### 5.4 항상 거부하는 파일 공유·메신저 주소 (계획)

`drive.google.com`, `dropbox.com`, `mega.nz`, `mediafire.com`, `wetransfer.com`, `cdn.discordapp.com`, `t.me`, 그 밖의 임의 파일 공유. 설치파일을 우회해서 받는 통로가 되기 때문이다.

### 5.5 경고만 하는 것 (계획)

`xn--` 로 시작하는 호스트(국제화 도메인 유사 문자), 사이트 이름과 비슷한 유명 서비스 이름이 도메인에 들어간 경우(사칭 의심). 운영자 승인 화면에 표시한다.

## 6. 사용자 입력 정리 규칙

원칙: **저장 시 검증하고, 출력 시 이스케이프한다.** 둘 다 한다. 현재 정적 사이트는 출력 시 `escapeHtml` 을 쓴다(구현됨). 폼 도입 후에도 HTML 을 허용하지 않는다.

| 입력 | 규칙 |
|---|---|
| 이름 | 1~60자, 제어문자·`<`·`>` 불가. 공백만 불가 |
| 한 줄 소개 | 1~200자, 줄바꿈 불가 |
| 설명 | 최대 4000자. **HTML 불가**. 마크다운을 쓴다면 HTML 을 끄고 링크·이미지 주소에 5.1 규칙을 적용한 파서를 쓴다. 원문은 그대로 저장하고 출력 때 변환 |
| 태그 | 최대 8개, 각 1~20자, 글자·숫자·공백·`-`·`_`·`#` 만. 소문자·공백 정리 후 저장. 중복 제거 |
| 카테고리 | 서버가 가진 목록(`lib/projects.mjs` `CATEGORIES`)에 있는 값만 |
| 링크 | 5절 규칙. 최대 8개. 이름(label)은 1~30자, 제어문자·`<`·`>` 불가. 화면에서는 항상 `rel="noopener noreferrer"`, 새 창 |
| 프로필 이름 | 1~30자, 제어문자·`<`·`>` 불가. 기본값은 임의 이름 |
| 이미지 | WebP 만, 1MB 이하, 가로·세로 4096 이하, 작품당 8장. SVG·GIF·PNG·JPEG 불가. **업로드 전 브라우저에서 재인코딩**하면 EXIF(위치 정보 등)가 사라진다. 서버 쪽 확인: 파일 앞 12바이트가 `RIFF????WEBP` 인지 정기 점검(버킷 설정은 선언된 형식만 본다). 파일명은 서버가 만든 이름(uuid)으로 저장, 사용자가 정한 이름 사용 금지 |
| 대체 텍스트(alt) | 최대 200자, 이스케이프 |

DB 에는 같은 제한을 `check` 제약으로 넣었다(초안). 폼에서도 같은 제한을 보여 줘서 사용자가 이유를 알게 한다.

## 7. 신고 → 즉시 비공개 → 검토 절차

1. **접수**: 로그인한 사용자가 공개 작품에서 "신고"를 누르고 사유(악성 파일, 피싱, 사칭, 저작권, 스팸, 부적절, 기타)와 설명을 낸다. 본인 작품은 신고할 수 없고, 같은 사람이 같은 작품을 중복 신고할 수 없으며, 하루 10건까지.
2. **즉시 비공개**(초안: 열린 신고 1건이면 자동): 작품 상태가 `hidden` 이 되어 공개 목록·작품 페이지에서 사라진다. 신고 시점의 이름·주소를 `reports.snapshot` 에 남긴다. 작성자는 수정·삭제할 수 없다(증거 보존).
3. **검토**(운영자, 목표 24시간 이내 — 목표일 뿐 약속이 아님): 신고 내용, 작품 링크(직접 열지 말고 URL 검사기·격리 환경에서 확인), 검사 기록을 본다.
4. **결정**
   - 문제 없음 → `admin_resolve_report(..., true)`: 신고 기각, 작품은 곧바로 공개하지 않고 `checking` 으로 보내 다시 검사한 뒤 공개.
   - 문제 있음 → `admin_resolve_report(..., false)`: 반려. 사유를 `review_note` 에 적는다. 심각하면 계정 정지(`profiles.suspended_at`).
5. **통지**: 작성자에게 비공개 사실과 사유를 알린다(방법은 결정 필요: 이메일 없이 사이트 안 알림으로 할지).
6. **기록**: 신고 id, 처리자, 시각, 결정, 메모를 남긴다(`reports`, `project_reviews`).
7. 악성 링크가 확인되면 Safe Browsing 에 신고하고 같은 호스트의 다른 작품도 점검한다.

허위 신고로 경쟁 작품을 내리는 남용이 가능하다. 완화: 로그인 필수, 일일 한도, 운영자 복구. 반복 허위 신고자는 정지한다. **자동 비공개 기준(1건 vs 여러 건)은 결정 필요**(11절).

**전문가 확인 필요**: 저작권·명예훼손 신고를 받았을 때 임시로 게시를 중단하는 의무·절차·기간, 이의 제기(재게시) 절차, 신고자·게시자 통지 의무는 법령(정보통신망법·저작권법 등)과 관련된다. 이 문서는 법적 기준을 정하지 않는다. 이용약관·신고 접수 안내문·개인정보 처리방침은 전문가 확인 후 작성한다.

## 9. 이미지 저장소의 알려진 한계

버킷은 공개(`public`)이다. 주소를 아는 사람은 누구나 읽는다(경로는 추측하기 어려운 uuid). 따라서 비공개로 돌린 작품의 이미지 파일도 Storage API 로 지울 때까지 주소로 접근된다. 대안: 비공개 버킷 + 서명 주소(만료·캐시 문제와 구현 복잡도가 늘어남). **결정 필요**.

## 10. 전문가 확인 필요 (이 문서가 정하지 않는 것)

## 11. 사람이 결정해야 할 것

1. 신고 자동 비공개 기준: 1건 즉시(현재 초안) vs 여러 건 또는 신고자 신뢰도 반영
2. 익명 신고 허용 여부(현재는 로그인 필수라 저작권·악성 신고를 하려는 비회원이 접수할 수 없음)
3. 확장 프로그램은 신뢰 계정이어도 항상 운영자 승인(현재 초안) 여부
4. 이미지 버킷 공개 vs 비공개+서명 주소
5. 스토어 허용 목록(5.3) 확정, 원스토어 도메인 확인
6. 글 수정(이름·설명)과 이미지 교체를 재검사 대상에 넣을지
7. 비공개·반려 통지 방법(이메일 없이 사이트 안 알림 등)
8. 검사 관련 파일 변경에 운영자 리뷰를 강제할지(CODEOWNERS·브랜치 보호)
9. 10절의 법적 항목을 맡길 전문가와 시점(공개 전 필수)
