# 주간실험실 방향성 (2026-11-25 기준)

이 문서는 사이트가 무엇을 위한 곳인지, 어떤 결정을 했는지, 앞으로 무엇을 할지를 적어 둔 기준 문서입니다. 화면이나 구조를 바꿀 때 먼저 여기와 어긋나지 않는지 봅니다. 방향이 바뀌면 이 문서를 먼저 고칩니다.

## 한 줄 정의

**처음 만든 웹·앱·확장 프로그램을 개발일지와 함께 올려 알리는 메이커 마켓.** 만드는 사람을 돕는 자료실(도구함)이 곁에 있다.

## 왜 만드는가

- 개발을 처음 해 보니 만드는 것보다 알리는 것이 훨씬 어려웠다. 그래서 "처음 만든 것을 보여 줄 곳"을 직접 만든다.
- 잘 만든 완성품 진열장이 아니라 **헤매고 고친 기록이 같이 있는 곳**이 목표다. 우당탕탕 개발 과정이 작품의 일부다.
- 최종 목표는 다른 사람들도 자기 창작물을 올리는 마켓플레이스다. 지금은 운영자의 작품 두 개(CertNote, 결제 기록장)로 구조를 만들고 검증하는 단계다.
- 해외 방문자에게도 알려지면 좋다. 그래서 영어 페이지를 처음부터 구조에 넣었다.

## 사이트 구조

```
/                홈: 첫 화면(이야기+검색) → 올라온 작품(종류·카테고리 필터) → 도구함 → 올리기 안내
/p/<id>          작품 페이지: 소개·기능·사용법·그 작품의 개발일지·자동 검사 결과
/submit          올리는 방법, 자동 검사 안내, 받지 않는 항목
/learn           개발 참고: UI 도감, Git·HTTP·정규식 도감, 겪은 문제(개발기) 목록
/dojang/...      UI 도감(실제 동작 데모 38개), 개발 참고 도감
/ai, /ai/<slug>  AI 활용: 프롬프트 작성법·예시·실수·용어
/trending        AI 스킬 어워즈: GitHub 에서 뜨는 AI 스킬(주간·오늘, 한국어 요약·태그)
/log, /log/<slug> 개발기 글(운영자가 서비스를 만들며 쓴 글)
/en, /en/p/<id>, /en/submit   영어 페이지(영어 소개가 있는 작품만)
```

- **작품**과 **도구함**을 섞지 않는다. 홈에서 작품이 먼저, 도구함은 그 아래 같은 카드 규격의 한 칸이다.
- 모든 섹션이 같은 머리(번호·제목)와 같은 카드 모양을 쓴다. 홈이 서로 상관없는 블록으로 쌓여 보이지 않게 한다. 어워즈의 어두운 무대는 `/trending` 안에만 둔다.
- 제목은 한국어 단어 단위로 줄바꿈한다(`word-break: keep-all`). 페이지 제목은 과하게 크게 하지 않는다.

## 데이터 모델

작품 하나 = `data/services.json` 항목 하나.

| 필드 | 설명 |
|---|---|
| `id`, `name`, `summary`, `status`, `url` | 필수. `status` 는 live / beta / building |
| `type` | `web` / `app` / `extension` |
| `category` | `lib/projects.mjs` 의 `CATEGORIES` 중 하나 (학습·교육, 생산성·도구, 금융·가계, 개발자 도구, AI, 생활·건강, 게임·재미, 디자인·미디어, 기타) |
| `author`, `since`, `tags`, `features`, `howto`, `links`, `stats` | 선택 |
| `name_en`, `summary_en` | 영어 소개. 둘이 함께 있어야 `/en` 에 나온다 |
| `thumbnail` | 카드 대표 이미지 경로(`src/img/` 아래). 없으면 분야 색과 종류별 틀로 대체 표시 |
| `screenshots` | 스크린샷 배열(문자열 또는 `{src, caption}`, 최대 8장). 작품 페이지 갤러리에 나온다 |
| `howto` | 사용법 단계. 문자열 또는 `{text, image}`. 경로가 틀리면 빌드가 멈춘다(`lib/media.mjs`) |

- 일지: `data/log.json` 의 `service` 가 작품 `id` 와 같으면 그 작품 페이지에 붙는다.
- 검사 결과: `data/checks.json` (자동 생성, 손으로 고치지 않는다).
- 잘못된 데이터는 빌드가 이유를 출력하고 멈춘다.
- **올리기 폼의 입력 정의**는 `data/schema/submission.json` 이다(공통 입력, 종류별 입력, 분야별 추가 질문, 이미지·사용법 규칙, 한도). 폼은 이 파일로 만들고, DB 는 같은 한도를 제약으로 다시 검사한다. 두 곳이 어긋나지 않는지는 `test/submission-schema.test.mjs` 가 확인한다. 종류·분야별 입력은 DB 의 `projects.details`(JSON)에 저장한다.
- 종류별 핵심: 웹은 서비스 주소, 앱은 스토어·배포 주소와 플랫폼·가격, 확장 프로그램은 GitHub 소스(필수)와 동작 범위·권한 이유. 금융·건강 분야는 "조언이 아님" 안내를 요구한다.

## 신뢰·안전 원칙

자세한 위협·규칙·절차는 [SECURITY.md](./SECURITY.md), 데이터베이스 초안은 `supabase/schema.sql`.

- "안전함"·"검증됨"이라고 쓰지 않는다. 무엇을 언제 검사했는지만 적는다. 자동 검사는 알려진 위험 신호만 잡는다.
- 받는 것은 텍스트·링크·이미지(WebP)뿐. 설치파일은 스토어·GitHub Releases 링크로만.
- 첫 작품은 운영자 승인, 주소 변경은 재검사까지 비공개, 신고가 들어오면 먼저 비공개 후 검토.
- 비밀 키는 서버 쪽에만, 프런트에는 공개(anon) 키만. 사용자가 올린 주소를 서버가 열 때는 내부 주소·리다이렉트·시간·크기를 제한한다.
- 약관·임시조치·개인정보 처리방침 같은 법적 판단은 전문가 확인 후 정한다(SECURITY.md 10절).

## 올리기와 자동 검사

지금 올리는 방법은 **GitHub PR** 이다(Supabase 폼으로 바꾸는 계획은 위 결정 기록, 구현 전)(정적 사이트라 서버가 없다). 올리는 사람은 개발자이므로 이 방식이 자연스럽다. 개발을 처음 하는 사람이 부담을 느끼면 나중에 폼 → 이슈 → PR 자동 생성으로 보강한다.

검사는 두 단계다.

1. **PR 단계** (`.github/workflows/check-pr.yml`): 빌드(데이터 형식), 단위 시험, `scripts/check-submission.mjs`. 비밀값이 없는 포크 PR 에서도 돈다. 주소 형식(https만, 단축 주소·IP·실행 파일 직접 다운로드 거부), 접속 확인, 확장 프로그램 권한·소스 패턴을 본다. 실패하면 PR 이 막힌다.
2. **병합 뒤** (`.github/workflows/check-main.yml`): Google Safe Browsing 과 VirusTotal 까지 돌리고 `data/checks.json` 에 기록한다. 주소가 바뀌었거나 7일이 지난 작품만 다시 검사한다.

원칙:

- **안전을 보장한다고 쓰지 않는다.** 화면에는 "자동 검사 통과 날짜"와 무엇을 검사했는지만 적는다. 키가 없어 건너뛴 검사도 "건너뜀"으로 그대로 적는다.
- 확장 프로그램은 소스가 있는 GitHub 저장소 주소(`links`)가 필수다.
- 넓은 권한(모든 사이트 접근, 쿠키, 방문 기록 등)은 막지 않고 화면에 알린다.
- 판정 로직은 `lib/checks.mjs`(순수 함수, `test/checks.test.mjs` 로 시험), 네트워크 호출은 `scripts/check-submission.mjs`.

## 영어 (해외 홍보)

- 영어 페이지는 `lib/en.mjs`. 영어 소개(`name_en`/`summary_en`)가 있는 작품만 `/en` 에 실린다.
- 모든 쌍의 페이지에 `hreflang`(ko / en / x-default)을 단다.
- 1단계: 홈·작품 카드·작품 페이지·올리기. 개발일지와 도구함 본문은 한국어 그대로 두고 한국어 페이지로 안내한다.
- 2단계(미정): 올리는 사람이 영어 소개를 못 쓰면 Claude 가 번역하게 하는 자동화.

## 도구함 (보조 자료)

작품 없이도 쓸 수 있고, 검색으로 들어오는 입구 역할도 한다. 새 자료를 늘릴 때도 "만드는 사람에게 도움이 되는가"를 기준으로 한다.

- **UI 도감**: 실제로 눌러 보는 데모 38개 (`data/dojang/ui-*.json`, `src/dojang/`)
- **개발 참고**: Git·HTTP·정규식 (`data/dojang/ref-*.json`)
- **AI 활용**: 프롬프트 작성법·예시·실수·용어 (`data/ai/*.json`, 운영자가 쓴 초안)
- **AI 스킬 어워즈**: GitHub Search API 로 뜨는 AI 스킬을 매일 갱신 (`scripts/fetch-trending.mjs`, `.github/workflows/trending.yml`). 별 수 순위일 뿐이라 안전·품질 보증이 아니며 화면에 경고를 둔다. 한국어 요약·태그는 `data/trending-ko.json`(새 항목은 `ANTHROPIC_API_KEY` 가 있으면 자동 요약).

## 아직 안 된 것 / 다음 순서

우선순위 순.

1. **배포**: Vercel 한도 초과로 `cert.juganlab.com` 이 HTTP 402 로 응답 중(2026-11-25 확인). Cloudflare Pages 로 옮긴다. 계획: `www.juganlab.com` 만 CNAME 으로 연결하고 루트는 www 로 리다이렉트, 이후 certnote 연결. 도메인이 www 가 되면 `lib/pages.mjs` 의 `SITE` 상수와 템플릿의 canonical·hreflang 주소를 같이 바꾼다. (DNS 작업은 운영자가 한다.)
2. **저장소 secret**: `GSB_API_KEY`, `VT_API_KEY`(검사), `ANTHROPIC_API_KEY`(트렌딩 한국어 요약). 없으면 해당 기능은 "건너뜀"으로 동작한다.
3. **올리기 안내 보강**: `/submit` 에 `category` 항목 설명 추가, 영어 카드에 카테고리 표시.
4. **남은 페이지 정리**: `/dojang/ui` 와 개별 도감, `/about`, `/ai` 하위, `/log` 를 새 디자인(작은 제목, 같은 카드 규격)에 맞춘다.
5. **AI 활용 고도화**: 상황 고르기, 빈칸 채워 만드는 프롬프트, 좋은/나쁜 프롬프트 비교.
6. **작품 늘리기**: 남의 작품이 올라오기 전까지는 운영자의 다른 서비스·확장을 추가해 목록의 밀도를 만든다.
7. **올리기 문턱 낮추기**: PR 대신 Supabase 폼·소셜 로그인. 구현 전에 `supabase/schema.sql` 을 개발용 프로젝트에 적용해 `supabase/RLS-TESTS.md` 를 통과시킨다.
8. **사이트 이름**: "주간실험실"이 마켓 성격에 맞는지 재검토.

## 하지 않기로 한 것

- 업로드한 실행 파일·압축 파일을 이 사이트가 직접 호스팅하지 않는다. 스토어나 저장소 링크만 받는다.
- "안전함", "검증됨" 같은 보증 표현을 쓰지 않는다.
- 영어 설명·태그를 한국어 화면에 그대로 노출하지 않는다(트렌딩은 한국어 요약만).
- 홈에 운영자 작품만 크게 띄우지 않는다. 모든 작품 카드는 같은 크기다.
