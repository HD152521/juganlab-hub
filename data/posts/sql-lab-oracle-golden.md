CertNote 의 SQLD 트랙에는 노트 안에서 바로 SQL 을 실행해 볼 수 있는 실습장이 붙어 있습니다. 노트의 예제 쿼리 아래에는 "실습장에서 실행하고 고쳐 보기"가, SQLD 퀴즈 해설 아래에는 "문제의 SQL 직접 실행해 보기"가 있습니다. 이 실습장은 서버에 데이터베이스를 두지 않고 브라우저 안에서 돕니다. 그리고 결과가 실제 Oracle 과 같은지를 골든 테스트로 확인합니다.

## 진짜 엔진을 쓰지 않은 이유

처음에는 브라우저에서 도는 진짜 데이터베이스를 붙이는 것이 가장 쉬워 보였습니다. SQLite 를 웹어셈블리로 옮긴 sql.js 나 Postgres 를 옮긴 PGlite 가 있습니다. 문제는 시험입니다. SQLD 는 Oracle 문법을 기본으로 하고, SQL Server 와의 차이를 묻는 문항이 섞입니다. `ROWNUM`, `CONNECT BY`, `(+)` 외부 조인, `NVL`, `DECODE`, Oracle 식 `PIVOT` 같은 시험 단골 문법이 SQLite 나 Postgres 에는 없거나 다르게 동작합니다. 시험 문법을 아예 못 돌리거나, 더 나쁘게는 틀린 결과를 보여 주게 됩니다.

미리 찍어 둔 결과만 보여 주는 방법도 검토했습니다. 정확하고 만들기 쉽지만, 정해진 쿼리만 돌아갑니다. 학습자가 조건을 바꿔 다시 쳐 보는 것이 실습장의 목적인데 그게 안 됩니다.

그래서 세 번째 방법을 골랐습니다. 시험에 나오는 범위의 Oracle 문법 해석기를 직접 만들고, 실제 Oracle 에서 돌린 결과와 대조합니다. 리눅스 셸 연습장에서 실제 Rocky Linux 컨테이너와 대조했던 것과 같은 구조입니다. 일이 크기 때문에 단계를 나눴습니다. SELECT·WHERE·함수·GROUP BY·조인을 먼저 열고, 서브쿼리·집합 연산·ROLLUP, 윈도우 함수·계층형 질의, PIVOT·정규 표현식·DML 순서로 주차 집필과 함께 넓혔습니다.

## 골든 환경

대조 상대는 Oracle Database Free 컨테이너(23ai)입니다. 시험 예제에 자주 나오는 EMP·DEPT·SALGRADE 테이블을 고정 데이터로 넣고, 사례 파일의 SQL 을 SQL*Plus 로 실행해 결과를 저장합니다. 결과를 기계가 비교할 수 있게 몇 가지를 맞췄습니다.

- 출력을 CSV 형식으로 받고, NULL 은 `<NULL>` 로 찍게 했습니다. 열 하나짜리 NULL 행이 빈 줄이 되어 사라지는 것을 막기 위해서입니다.
- 날짜 표시 형식, 날짜 언어, 소수점 기호를 세션에서 고정했습니다.
- DML·DDL 처럼 여러 문장으로 된 사례는 한 세션에서 차례로 실행하고, 끝나면 되돌리고 만든 테이블과 뷰를 지워 다음 사례에 영향을 주지 않게 했습니다.

사례는 세 곳에서 옵니다. 직접 쓴 경계 사례, SQLD 노트에 들어 있는 SQL 블록 전부, 실습 과제의 모범 답안입니다. 노트의 결과표도 손으로 쓰지 않고 컨테이너에서 실행한 결과를 붙였습니다.

## 건수가 늘어난 과정

| 시점 | 골든 대조 건수 |
|---|---|
| 첫 공개(1~4주차 범위) | 382 |
| 6주차(윈도우 함수·계층형 질의) | 750 |
| 7주차(PIVOT·정규 표현식·DML) | 863 |
| 11월 5일 엔진 차이 수정 뒤 | 957 |

건수는 노트와 과제가 늘어날 때마다, 그리고 검토에서 차이가 발견될 때마다 늘었습니다. 주차를 올릴 때마다 검토 에이전트가 노트와 엔진을 함께 검토했고, Oracle 과 결과가 다른 쿼리를 찾으면 골든 사례로 더했습니다.

## 시험 기준과 23ai 가 다른 곳

대조하다 보니 최신 Oracle 23ai 가 시험이 전제하는 동작과 다른 곳이 있었습니다. 23ai 는 `FROM` 없는 `SELECT` 를 받아 주고, `GROUP BY` 와 `HAVING` 에서 SELECT 별칭을 쓸 수 있습니다. 시험 문제는 이런 쿼리를 오류로 봅니다. 실습장은 이 경우 시험 기준대로 오류를 내되, 최신 버전에서는 동작한다는 설명을 함께 붙입니다. 테스트에도 이 차이 목록을 따로 적어 두었습니다.

## 모르는 것은 모른다고 말하기

아직 구현하지 않은 문법을 만났을 때 가짜 Oracle 오류 번호를 내면, 학습자는 자기 쿼리가 틀렸다고 오해합니다. 그래서 단계별로 열리지 않은 기능은 "n단계에서 열린다"는 안내를 냈습니다. 정규식 백트래킹이나 큰 DML 로 탭이 멈추지 않도록 엔진은 Web Worker 에서 돌리고, 4초가 넘으면 끝냅니다. 큰 교차 조인 위의 계층형 질의처럼 계산이 오래 걸리는 쿼리는 결과 대신 상한 안내가 나옵니다.

## 남겨 둔 차이

검토에서 나온 차이 중 희귀 문법은 백로그 문서에 모아 두고, 고칠 때마다 골든 사례를 더한 뒤 목록에서 지웁니다. 11월 5일에는 그중 7건을 한꺼번에 고쳤습니다. `RENAME COLUMN` 이 문자열 리터럴 속 글자를 열 이름으로 착각해 CHECK 제약을 다시 만들던 것, `NUMBER(p,s)` 에서 s 가 p 보다 크거나 음수일 때, 짧은 문자열로 날짜를 CAST 할 때의 오류, `PIVOT` 의 IN 값이 겹칠 때의 오류 등입니다.

일부러 따라가지 않은 것도 있습니다. Oracle 23ai 는 `WHERE 'A ' = 'A'` 에서는 참을 내지만 `CASE WHEN` 이나 `DECODE` 안에서는 거짓을 냅니다. 상수 접기의 결과로 보이는 동작이라 엔진은 어디서나 같게 두었습니다. 동점 행의 정렬 순서가 Oracle 과 반대로 나오는 경우도 있는데, Oracle 도 보장하지 않는 순서라 결과가 틀린 것은 아닙니다. 이런 차이는 숨기지 않고 문서에 적어 두었습니다.

실습장 과제는 결과 집합으로 채점합니다. 같은 결과를 내는 다른 쿼리도 정답입니다. SQLD 모의고사 100문항 중 SQL 의 결과나 오류를 묻는 문항도 Oracle 23ai 에서 실행해 정답을 확인했습니다.
