검색에 노출되려면 먼저 검색 로봇이 페이지를 읽어 가야 합니다. 그런데 로봇이 한 사이트에 쓰는 시간은 무한하지 않습니다. 쓸모없는 주소를 많이 돌게 만들면, 정작 읽혀야 할 노트가 뒤로 밀립니다. CertNote 의 색인 숫자가 기대만큼 늘지 않아 원인을 찾던 중, 로봇의 방문이 엉뚱한 곳에 쓰이던 경로를 세 가지 찾았습니다.

## 1. 없는 주소가 200 으로 나가고 캐시되던 문제 (10월 22일)

`/aws/saa-c03/week99/day1` 처럼 존재하지 않는 일차 주소를 열면 "찾을 수 없음" 화면이 나왔습니다. 문제는 그 응답의 상태 코드였습니다. 404 가 아니라 200 이었고, 그 응답이 캐시까지 됐습니다. 검색엔진은 이런 페이지를 "소프트 404"로 분류합니다. 겉으로는 정상 페이지인데 내용은 비어 있는 주소가 얼마든지 생길 수 있는 구조였습니다.

원인은 루트에 둔 로딩 화면이었습니다. 로딩 화면을 먼저 흘려보내는 스트리밍 때문에, 페이지 안에서 "없음"을 판정하는 시점에는 이미 상태 코드 200 이 확정되어 있었습니다.

고치는 과정이 순탄하지는 않았습니다. 처음 세 번의 시도는 "막아야 할 주소 모양을 나열하는" 방식이었는데, 검수할 때마다 나열에서 빠진 새 구멍이 나왔습니다. 네 번째에 방식을 바꿨습니다. 일차 페이지를 `aws`, `linux`, `en` 같은 실제 섹션 이름의 폴더 아래로 옮겨, 지원하지 않는 분류의 주소는 라우터가 처음부터 매칭하지 않게 했습니다. 그리고 요청이 페이지에 닿기 전에 주소를 분류하는 순수 함수를 두어, 콘텐츠 주소처럼 생겼지만 콘텐츠가 아닌 경로와 대소문자만 다른 경로를 렌더 전에 404 로 돌렸습니다. 1주차도 해당 일차 파일이 실제로 있는지 확인하게 했습니다. 없는 주소 13종을 두 번씩 요청해 두 번 모두 404 인지 보는 테스트도 넣었습니다. 두 번째 요청까지 보는 이유는 첫 응답이 캐시된 뒤에도 404 가 유지되는지 확인하기 위해서입니다.

## 2. 수집되는 페이지의 40% 가 noindex 였다 (10월 23일)

다음 날에는 로봇이 실제로 무엇을 보는지 흉내 내 봤습니다. 홈에서 시작해 링크를 따라가며 페이지를 모으니 1,443개가 모였고, 그중 40%인 597개가 `noindex` 페이지였습니다. 대부분 아직 번역하지 않은 영어판 주차였습니다. 사이드바, 자격증 목록, 이전·다음 버튼이 이 페이지들로 링크를 걸고 있었습니다. 로봇은 링크를 따라가 읽었다가 "색인하지 말라"는 표시를 보고 돌아서는 일을 수백 번 반복하고 있었던 셈입니다.

번역 전 영어판 주차로 가는 링크를 한국어 원문으로 돌리고, 목록에는 한국어로 연결된다는 표시를 붙였습니다. 다시 재 보니 수집되는 페이지는 873개, 그중 `noindex` 는 의도한 후기 페이지 27개만 남았습니다. 같은 작업에서 일차 페이지 제목 앞의 "Day N -" 을 떼고, 허브 페이지 제목에 사람들이 실제로 검색하는 말("공부", "순서", "공부법", "무료")을 넣었습니다.

## 3. 크롤링의 88% 가 RSC 요청이었다 (11월 9일)

세 번째는 Search Console 의 크롤링 통계에서 나왔습니다. 11월 7일 기준으로 로봇이 가져간 파일 형식은 "다른 파일 형식"이 88%, HTML 이 7% 였습니다. 목적은 "새로고침"이 99%, "검색(새 페이지 발견)"은 1% 미만이었습니다. 로봇이 HTML 은 거의 읽지 않고 다른 무언가를 계속 다시 받아 가고 있었습니다.

그 무언가는 `?_rsc=` 가 붙은 요청으로 봤습니다. CertNote 는 Next.js 로 만들었고, 화면에 보이는 링크의 다음 페이지 데이터를 미리 불러오는 기능이 있습니다. 이 미리 불러오기 요청은 HTML 이 아니라 React 서버 컴포넌트 데이터를 받아 가는데, 주소 끝에 `?_rsc=` 가 붙습니다. 노트 본문은 서버가 그린 HTML 에 이미 다 들어 있으므로, 검색 로봇에게 이 데이터는 필요 없습니다. robots.txt 에서 `?_rsc=` 와 `&_rsc=` 가 붙은 주소를 막고, 막는 규칙을 테스트로 고정해 배포했습니다. 같은 날 모의고사로 가는 링크의 미리 불러오기도 껐습니다.

이 조치의 효과는 아직 모릅니다. 크롤링 통계는 늦게 반영되기 때문에, 11월 20일 무렵 HTML 비율이 올라갔는지 다시 보기로 했습니다. 같은 통계에서 DNS 오류가 2% 로 나왔는데, 이것은 도메인 설정을 바꾸는 문제라 따로 결정을 기다리고 있습니다.

## 지금 숫자와 판단

11월 10일 Search Console 기준으로 색인된 페이지는 107개, 색인되지 않은 페이지는 약 1,980개입니다. 그 안을 나눠 보면 이렇습니다.

- `noindex` 827개: 영어판 2주차 이후입니다. 한국어가 섞여 있어 일부러 닫아 둔 것이라 그대로 둡니다.
- 크롤링됨 - 색인 안 됨 832개: 표본은 한국어 노트와 예전 주소(새 주소로 넘어가는 것은 정상)였습니다. 본문은 1~2만 자, 응답은 0.3~1.2초, 내부 링크도 정상이었습니다. 그래서 기술 문제보다는 외부 링크와 방문이 적은, 사이트 신뢰도의 문제로 판단했습니다.
- 발견됨 - 색인 안 됨 309개: RSC 요청이 크롤링을 차지하던 문제와 맞물린 것으로 보고 있습니다.

검색 속성을 지우고 다시 등록하면 어떨까도 검토했지만 하지 않기로 했습니다. 색인 상태는 그대로이고 기록만 사라지기 때문입니다. 대신 국내 유입이 큰 네이버와 빙에 바뀐 주소를 바로 알리는 IndexNow 제출 스크립트를 만들었습니다. 첫 제출에서 네이버는 908개 주소를 접수했고, 빙 쪽은 키 확인이 끝나지 않아 다시 보내기로 했습니다.

세 가지를 겪고 나니 기준이 생겼습니다. 사이트가 크면 검색 로봇에게 "어디를 읽지 말아야 하는지"를 알려 주는 일도 콘텐츠를 늘리는 일만큼 중요합니다.
