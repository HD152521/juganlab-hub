구독제를 접고 모든 주차를 공개한 다음 날, 본문 페이지의 속도를 손봤습니다. 유료 벽이 있던 동안 2주차 이후 본문은 방문할 때마다 쿠키를 읽어 권한을 확인해야 했기 때문에 캐시할 수 없었고, 요청마다 서버가 페이지를 새로 그렸습니다. 유료 벽이 꺼져 더는 쿠키를 읽을 이유가 없어졌으니 캐시할 차례였습니다.

## 세 가지 선택지

대상은 2주차 이후 일차 파일 1,257개(한국어 687, 영어 570)였습니다. 검토한 방법은 셋입니다.

- **A. 빌드 때 전부 미리 만들기**: 가장 단순하지만 빌드 시간이 크게 늘 수 있습니다.
- **B. 빌드 때는 만들지 않고, 첫 요청 때 한 번 만들어 캐시하기**: 빌드 시간은 그대로입니다.
- **C. 라우트는 동적으로 두고 CDN 캐시 헤더만 붙이기.**

추측으로 고르지 않고 로컬에서 직접 빌드해 쟀습니다. 매번 빌드 산출물을 지우고 처음부터 빌드한 값입니다.

| 빌드 | 전체 시간 | 비고 |
|---|---|---|
| 당시 방식(요청마다 렌더) | 213~280초 | 미리 만드는 200장 중 40장이 60초 제한에 걸려 재시도 |
| B 임시 적용 | 161~176초 | 재시도 없음 |
| A 임시 적용 | 실패 | 1,457장 중 143장에서 중단, 60초 초과 318건 |

A 는 로컬에서 빌드 자체가 끝나지 않았습니다. 같은 구성에서도 시간이 161초에서 280초까지 흔들렸기 때문에, 당시 방식과 B 의 차이는 측정 오차로 봤습니다. 확인된 사실은 "B 는 빌드 시간을 늘리지 않는다"였습니다.

B 를 고른 이유가 하나 더 있습니다. 노트는 저장소의 마크다운 파일이라, 내용이 바뀌는 시점은 곧 배포 시점입니다. 배포하면 캐시가 새로 시작되므로 재검증 주기도, 캐시를 지우는 API 도 필요 없습니다. 로컬에서 B 의 응답 시간을 재 보니 서버 프로세스의 첫 렌더는 5.6초, 그 뒤 다른 일차의 첫 요청은 0.32~0.78초, 두 번째 요청부터는 0.011~0.023초였습니다. 운영 환경에서 얼마나 빨라졌는지는 그때 재지 못했습니다.

## 다시 켜면 깨지게 하는 가드

캐시에는 위험이 하나 따라옵니다. 누군가 나중에 유료 벽을 다시 켜면, 잠겨야 할 본문이 이미 공개 캐시에 남아 있게 됩니다. 그래서 유료 벽 스위치를 다시 켜면 빌드와 캐시 계약 테스트가 실패하도록 막았습니다. 본문 페이지가 쿠키나 동적 API 를 불러오면 역시 테스트가 실패합니다. 주소도 엄격하게 했습니다. `day1abc` 나 `week02` 처럼 정규형이 아닌 주소는 캐시되기 전에 404 가 됩니다.

## 홈이 느렸던 이유

같은 시기에 홈의 첫 응답도 쟀습니다. 운영에서 연속으로 여섯 번 요청하니 첫 요청이 4.1초, 그 뒤로는 0.2~0.5초였습니다. 계획서에 적혀 있던 "홈 3.3초"는 평소 속도가 아니라 서버 함수가 식었을 때의 첫 응답이었습니다. 홈에는 캐시가 없어서, 함수가 식을 때마다 이 지연이 방문자에게 그대로 갔습니다.

원인은 홈 코드의 한 줄이었습니다. 로그인한 사용자인지 확인하려고 쿠키를 읽는 호출 하나 때문에 홈 전체가 동적 페이지가 되어 있었습니다. 홈을 둘로 나눴습니다. `/` 는 쿠키도 세션도 데이터베이스도 읽지 않는 정적 랜딩만 그립니다. 요청이 들어오면 앞단의 프록시가 세션 쿠키의 서명과 만료만 확인하고, 유효하면 로그인 사용자용 학습 홈(`/home`)을 같은 주소로 보여 줍니다. 서버가 처음부터 맞는 화면을 내보내므로 깜빡임이 없습니다. 로컬에서 홈의 첫 요청은 1.03초에서 0.04초가 됐습니다.

## HTML 의 78% 가 사이드바였다

속도와 함께 페이지 크기도 봤습니다. 홈 HTML 은 344KB 였는데, 그중 268KB 가 사이드바에 넘기는 데이터였습니다. 일차 1,377개가 객체 하나씩 페이지 데이터에 실려 있었고, 일차마다 분류·자격증 이름·주소가 반복됐습니다. 처음에는 "사이드바와 모바일 메뉴 두 곳에 넘겨서 두 번 실린다"고 짐작했지만, 실제로 재 보니 React 가 같은 객체를 한 번만 싣고 있었습니다. 짐작은 틀렸고, 문제는 형식의 낭비였습니다.

일차 목록을 `[주차, [[일차, 제목], …]]` 모양의 짧은 배열로 바꾸고, 주소는 브라우저에서 다시 조립하게 했습니다. 사이드바 데이터는 269KB 에서 116KB 로 줄었고, 홈 HTML 은 344KB 에서 191KB(압축 후 65KB 에서 51KB)가 됐습니다. 화면에 그려지는 마크업은 그대로였습니다. 스크립트 경로와 요청마다 바뀌는 값을 빼고 비교하면 바뀌기 전과 바이트 단위로 같았습니다.

남은 116KB 의 대부분은 일차 제목입니다. 사이드바를 나중에 불러오면 더 줄일 수 있지만, 그러면 처음 HTML 에 들어 있던 같은 자격증의 일차 링크 약 60개가 사라집니다. 그때는 검색 색인 문제를 고치는 중이었기 때문에 내부 링크가 줄어드는 변경은 넣지 않았습니다. 빠르게 만드는 일도 결국 검색과 함께 저울질해야 했습니다.
